# Firestore rules analysis

Target: `viewcast2/(default)` (Standard edition, Native mode).

## Codebase findings

- The web client uses Firebase Authentication and a single Firestore path:
  `users/{uid}`.
- Reads use direct `getDoc()` calls. There are no collection queries,
  `where()`, `orderBy()`, or `limit()` clauses.
- Profile writes use `setDoc(..., {merge: true})` with `uid`, `email`,
  `displayName`, and server timestamps.
- YouTube connection writes merge `youtubeConnections`, with a legacy
  `youtubeConnection` field still supported.
- Channel-context writes merge optional `channelTopic` (0-120 characters) and
  `channelContext` (0-1000 characters) into the owner profile and update the
  server-controlled `updatedAt` timestamp.
- User documents contain PII and are owner-readable only.
- The AI callable function uses Firebase Authentication separately from
  Firestore. Both systems require a verified email before protected access.

## Devil's advocate audit

1. Public list: denied by default.
2. Cross-user read/write: denied by UID ownership checks.
3. Update bypass: blocked by applying `isValidUser()` to create and update.
4. Ownership hijacking on create/update: blocked by document ID, Auth UID, and
   immutable stored UID checks.
5. Timestamp integrity: `createdAt` is server-generated on creation and
   immutable afterward; legacy profiles without it cannot inject it later.
   `lastSignInAt` must remain unchanged or use the current server time.
6. Type juggling and required-field omission: blocked for the known profile
   schema.
7. Oversized profile strings, channel-context strings, and connection arrays:
   bounded. Context fields also enforce string types on create and update.
8. Privilege escalation and schema pollution: no role fields are accepted and
   unknown fields are rejected.
9. Unverified-email access: denied using the trusted Auth token claim.
10. Mixed-content leak: the PII-bearing user document remains owner-only.
11. Orphaned subcollections: no subcollection rules exist, so access is denied.
12. Query mismatch: the app performs only owner document gets, which the rules
    allow after authentication.
13. Context update bypass: blocked because `isValidUser()` validates both
    optional context fields on create and every update.
14. Context cross-account injection: blocked by authenticated UID ownership; no
    authenticated user can write another user's context.

Numeric analytics, connection timestamps, strings, nested connection maps, and
the connection list are type-checked and bounded. The fixed five-item maximum
allows every nested connection entry to be validated individually.
